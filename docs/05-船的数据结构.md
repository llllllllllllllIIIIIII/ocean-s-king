# 船的数据结构设计（待你核实）

> 这份文档是 Day 1 剩下那半天的施工依据：`data/ship.json` 到底长什么样。
> 目标是**改船 = 改数据**，不改代码。

---

## 1. 三层对象模型

把"船的定义""船的运行时状态""船的渲染"彻底分开。基地/载具类游戏最容易栽在把它们揉在一起。

| 层 | 是什么 | 存哪 | 谁改它 | 谁读它 |
|---|---|---|---|---|
| `ShipDef` | 结构：几层、每层格子、设施位置、帆装尺寸 | `data/ships/*.json` | 你和我，改数据 | 所有人 |
| `Ship` | 运行时状态：位置、艏向、横倾、帆角、损伤、载货 | 内存 | 物理 / 船员系统 | 渲染、UI |
| `ShipView` | 渲染：按层画格子与 SVG 部件 | 内存 | 只读 | 摄像机 |

### 铁律

> **`ship.json` 里绝不出现会随时间变化的值。**

不写"当前速度""当前帆角""剩余淡水""船员在哪"。
只写结构和**初始值**（比如损伤初始 = 1.0）。

破了这条，存档、重开、无头测试会同时变难——因为"数据文件"和"游戏进度"混成了一锅。

---

## 2. 关键决定一：所有层共用一张 20×6 网格

四层不是各自一套坐标，而是**同一个足迹垂直堆叠**：

```
       x=0 (船首) ─────────────────────────► x=19 (船尾)

L3  桅顶瞭望台    elevation +12 m   [ 一小块平台，其余格子 = 船外空气 ]
L2  主甲板        elevation   0 m   [ 20 × 6 格子 ]
L1  下层甲板      elevation  -2 m   [ 20 × 6 格子 + 房间标注 ]
L0  货舱          elevation  -4 m   [ 20 × 6 格子 + 房间标注 ]

       y=0 ………………………………………………………… y=5
       (左舷)                                    (右舷)
```

**为什么这样做**

- 跨层连接变成"同一个 (x, y)，换一个 z"——梯子就是 `(10, 3, L2 → L1)`，零坐标换算。
- 四层索引方式完全一致，渲染、寻路、校验各写一遍就够。
- 这是《矮人要塞》的做法，被验证过。

**注意**：不是每层都有完整结构。L3 大部分格子是"船外空气"，L0/L1 的尖船首处也是。
这些格子照常存在，只是标成 `outside`，索引不会错位。

---

## 3. 关键决定二：格子是底层表示，房间是格子上的语义标注

原文要求是"主甲板用格子，里面用房间"。落地方式是：

**运行时只有一套格子图。房间是贴在格子上的标签。**

| | 创作时 | 运行时 |
|---|---|---|
| 甲板层 L2/L3 | 你直接关心每个格子放什么（1 米/格） | 格子图 |
| 舱内层 L0/L1 | 你按**房间**划分（一个房间 = 一组格子 + 用途） | 同一张格子图，房间是元数据 |

同一个"厨房"有两副面孔，但底层只有一套：

- **玩家 / 工作系统** 看到的是**房间** —— 指派任务时说"去厨房做饭"
- **寻路 / 渲染 / 碰撞** 看到的是**格子** —— 实际走的是那 4 个格子

如果真做成两套独立表示（格子图 + 房间图 + 门洞连接），跨层寻路和渲染要写两遍，7 天不够。

---

## 4. 关键决定三：静态结构分两类 —— 格子 vs 物件

| | 格子 Tile | 物件 Prop |
|---|---|---|
| 是什么 | 地形 | 有状态的实体 |
| 例子 | 甲板、舷墙、舱口开口、梯子、墙、舱内地板、船外空气 | 桅杆、帆、舵柄、绞盘、铺位、灶台、水桶、货堆 |
| 有状态吗 | 基本没有 | **有**：损伤、占用、朝向、帆角、内容物 |
| 能走上去吗 | 由它决定 | 通常占着格子，可交互 |

**为什么帆要单独拎出来**：帆挂在甲板**之上**，根本不在格子图里。
所以帆装是独立的一块数据，与甲板解耦——这也正好对应"玩家不直接操船、船员去调帆"：
帆是**被人操作的物件**，不是地形。

---

## 5. 文件布局：类型 vs 实例

```
data/
  defs/
    tiles.json            格子类型表：. 船外 / # 甲板 / = 舷墙 / H 舱口 / L 梯子 …
    props.json            物件类型表：桅杆 / 帆 / 舵 / 绞盘 / 铺位 / 灶台 / 水桶 …
  ships/
    caravel_60.json       一艘具体的船（实例）
```

**分开的理由**：以后要做第二艘船、或玩家换船，只加一个实例文件，
`defs/` 不动、代码不动。

## 7. 跨层寻路：一张图

把所有层的可走格子 + 所有 link 拼成**一张图**，寻路只跑这一张：

```
   节点 = 可走格子 (x, y, layer)
   边 A = 同层四邻接        代价 1.0
   边 B = link（梯子/舱口）  代价 3.0   ← 爬梯子慢，所以布局会影响效率
```

几条具体约定：

- 船员只有一个 `current_layer`，渲染时**只画当前层的船员**，其他层的看不见（这正是分层视图的意义）。
- 梯子走得慢（代价 3.0），所以"把厨房放在船前部、铺位放在船尾部"会真的让人变累。
  这是免费得到的游戏性。
- 舱口 `hatch` 和梯子 `ladder` 在寻路上等价，区别只在渲染和"能不能搬大件"（后续）。

## 8. 避免一个必然会踩的坑：外形必须同源

甲板格子的外形和 `hull_outline.svg` **必须来自同一个来源**。

否则 Day 2 一定会出现"甲板比船壳宽了两格""船首的甲板戳出船体"这种事，
而且这种错很难看出原因。

**方案**：用一组船体参数同时生成两样东西

```
船体参数（长度 20 / 最大宽 6 / 艏部收窄曲线 / 艉部截断位置）
        │
        ├──► L2 主甲板的 tile map 外形（哪些格是 # / = / .）
        └──► assets/ship/parts/hull/hull_outline.svg 的路径
```

一个源，两处用，永远对得上。改一次参数，甲板和船壳一起变。
第 6 节里的 `"tiles"` 示意串只是说明格式，真正的字符串由这个生成器产出（可以手工微调）。

## 9. 静态 vs 运行时：边界划在哪

| 进 `ship.json`（结构） | 不进（运行时状态） |
|---|---|
| 几层、每层多少格 | 船员现在在哪一格 |
| 每层每个格子是什么 | 帆的当前收放角 |
| 设施摆在哪 | 船的当前速度、艏向、横倾 |
| 房间的用途标签 | 淡水还剩多少 |
| 帆的面积、帆桁长度 | 桅杆/船体/舵的当前损伤 |
| 损伤的**初始值** | 谁和谁关系不好 |

## 10. 坐标与摄像机

**船内一律用船局部坐标**（+x 船首、+y 右舷、原点 = 桅杆底座）。
船在世界里的姿态只有三个量：`position` / `heading` / `heel`。

在 Godot 里就是：`Ship` 是一个 `Node2D`，各层是它的子节点，
船的移动旋转自动带着船员和图一起动，不需要给每个船员算世界坐标。

**画面朝向我们选"世界北朝上、船自己转"**（不是把世界转过来）。
理由：帆的收放角、风向、船首向三者的关系是这套玩法的核心，
固定北向才能让玩家一眼看出"帆相对风和船是什么角度"。
并且这样主视角和帆态面板的矢量图**方向一致**，不用在脑子里做旋转。

## 11. 数据校验器（Day 1 就做）

`data/ship.json` 是手写的，手写就一定会有错，而且错了往往表现为"某个船员莫名其妙不动了"这种难查的现象。

所以配一个校验器 `tests/validate_ship.gd`，用 headless 跑（我们已验证 headless 可行）：

1. 每层的行数 = `cells_y`，每行字符数 = `cells_x`
2. 每个格子字符都在 `tiles.json` 里有定义
3. 每个 link 的 from/to 层都存在，且两个格子都是可走的
4. 从 L2 出发，所有层都可达
5. 每个 room 的格子都真实存在、可走，且房间标记不重叠
6. 每个 prop 都落在合法格子上，且没有两个 prop 抢同一格
7. `rig` 至少有一根桅杆，每面帆面积 > 0

任一条不满足就**报错退出并打印格子坐标图**，而不是悄悄继续。

## 12. 为什么不用 Godot 的 TileMap 当数据源

Godot 有现成的 `TileMapLayer`，能用编辑器刷格子，看起来更省事。但：

| | JSON 当真源 | TileMap 当真源 |
|---|---|---|
| 无头测试 | 直接读，容易 | 要起场景树 |
| 版本管理 diff | 一行一个字符，好看 | 二进制/复杂资源，难看 |
| 与 SVG 拼装配合 | 天然 | 要额外桥接 |
| 编辑器可视化编辑 | 需要自己写调试视图 | 白送 |

**结论：JSON 是真源，编辑器里的可视化只当"视图"。**
Day 1 的自绘调试视图足够用；如果以后刷格子刷得烦了，
再写一个"JSON ↔ TileMap"的导入导出即可，不影响架构。

## 13. 待你确认的四个点

1. **所有层共用 20×6 网格**（而不是每层独立尺寸）——接受吗？
   接受的话跨层连接极简；不接受的话我需要在 link 里做坐标映射。
2. **格子 vs 房间**：接受"底层统一为格子、房间是格子上的一层标签"吗？
   （也就是房间仍然存在，只是不作为独立的寻路结构。）
3. **甲板外形由船体参数生成**（而不是手工摆格子）——接受吗？
4. **舱内格子的粒度**：L1/L0 也用 1 米/格（和甲板一致），还是用 2 米/格更省事？
   1 米更精细但数据量翻四倍（不过 20×6×2 层也就 240 格，其实无所谓，我倾向 1 米保持一致）。
