## 1. 这一版要做什么

**一句话**：从"一个人开一条船走一趟"变成"**四个船长在同一个大西洋上各自开一条船，走完塞维利亚到巴西的一段真实航程**"。

### v0.5 完成时，能演示什么

1. 两台（或四台）机器连同一个局域网，各自开一艘船，同一片海、同一套风、同一批港口；
2. 从塞维利亚（圣卢卡尔）出发，经加那利、佛得角，抵达巴西海岸 —— 途中要补给、要修船、要买货；
3. 上岸探索时可能和当地群体打起来：火绳枪齐射、轻型炮、会死人；
4. 船上的四十个人会饿、会累、会闹、会抱怨，玩家靠"规则"来管；
5. 全队抵达终点后，拿到一份**船队级**的最终结算（财富 / 航海 / 知识 / 船员 / 历史 五类成果）。

### 与 v0.1 的关系

v0.1 已经把最难的三条链子立住了：**气动**（风 → 帆 → 船）、**指挥链路**（玩家 → 航海官 → 船员 → 帆）、**分层船体**（4 层 + 船员在船内生活）。v0.5 不推翻它们，只做两件事：

- **把"一条船的世界"扩成"多艘船的世界"**（世界分块、海图、网络、抽象船）；
- **把"只有海"扩成"海 + 岸 + 人"**（港口、资源、贸易、船员社会、陆战与火器）。

基线（v0.1 收工，必须每期都保持全绿）：

```
validate_ship 176 / test_svg_parts 81 / test_aero_polar 15 / test_command_chain 17 /
test_crew 84 / test_world 62 / test_story 90 / test_ship_debug_logic 20 /
check_motion_ownership ✅
```

### 为什么只规划到 v0.5

原始设定文档有 44 节，v0.5 覆盖其中 28 节左右。剩下的（船对船海战、葡萄牙追捕、多结局评分、环球剩余航段、船队编队、Steam）留到 v0.6+ 再排。理由很简单：**一段航程 + 联机 + 陆战** 已经是一个能独立成立、能被别人玩、能被验收的产品；把它做扎实，比把地图摊到全球更有价值。

### M1 · 状态地基 + 存档

**目标**：把"一局的所有状态"拆成三层，并让它能被完整存下来、读回来。网络与存档要的是同一样东西 —— **清楚的状态边界**，所以这一期同时为 M3 铺路。

**任务**

| 项 | 内容 |
|---|---|
| 状态分层 | `WorldState`（共享：时钟/风种子与突变序列/全局事件旗标/港口库存与价格/已发现地图/抽象船）与 `ShipState`（每艘船：位姿/帆/三处损伤/资源/锚/登陆队/名册摘要），两者都由 JSON 可序列化 |
| 存档 | `SaveGame`：`user://saves/<slot>.json`，字段 `version / saved_at / world / ships[] / journal / story`；版本不符直接拒绝并提示 |
| 架构文档 | 新写 `docs/14-状态与网络架构.md`：权威归属、字段清单、序列化形状、升降级规则 —— 先写文档再动代码 |
| 存档 UI | 主菜单/暂停里最简的"存档 / 读档 / 返回主菜单"（不追求好看） |
| 兼容 | 读档后 `Voyage` 的既有行为（风、洋流、剧情、船员）必须和连续跑出来的一样 |

**产出物**：`scripts/world_state.gd`、`scripts/ship_state.gd`、`scripts/save_game.gd`、`docs/14-状态与网络架构.md`、`tests/test_save.gd`。

### M2 · 世界分块 + 大西洋海图

**目标**：把 8km 的方块海，换成"一块一块拼起来的大西洋"，并且让玩家能在海图上看见自己把未知变成已知的过程。

**任务**

| 项 | 内容 |
|---|---|
| 分块 | `WorldMap`：16km × 16km 的 tile 网格。**tile 尺寸 = 2×瞭望视野（8km）**，所以站在 tile 中央时，视野边界正好是 tile 边界 —— 跨块时不会"看见新的地形突然冒出来" |
| 无缝 | 玩家在局部视图里开出 tile 边界时，相邻 8 块已经预载好；**同一坐标在任何 tile 采样必须得到同一结果**（这是这一期最重要的断言） |
| 海图 | 手绘大西洋海图（伊比利亚、西非、加那利、佛得角、巴西海岸），已发现区域着色、未探索区域起雾 |
| 相机 | 沿用 v0.1 的设计哲学：**同一台相机连续缩放**，船舱 → 甲板 → 局部海域 → 海图；地形与海图符号交叉淡入 |
| 时间 | 加真实日期（1519-09-20 起），海图与航海日志都按日期记 |

**产出物**：`scripts/world_map.gd`、`scripts/chart_view.gd`、`data/world/atlantic/*.json`、`tests/test_worldmap.gd`、一组"跨边界"截图。

**验收标准**

1. `tests/test_worldmap.gd`：在 tile 边界两侧各采样同一位置，地形/礁/港/地标/洋流结果完全一致；
2. 截图：船从 tile A 开到 tile B，地形不跳变、不发白、不重影；
3. 拉到最远能看到整张海图，未探索区域是雾；
4. 既有 8 通道全绿。

**砍单预案**：先做固定 3×3 = 48km 的可航区 + 一张简化海图；分块机制保留，内容后补。

### M3 · 局域网层（最高风险）

**目标**：2–4 个人各自开一条船，在同一个世界里待上十分钟，两边的世界不会越走越远。

**任务**

| 项 | 内容 |
|---|---|
| 权威 | 房主跑 `WorldState`（时钟、风、全局事件、港口库存与价格、AI 船、存档）；每个玩家跑自己那艘船的 `Ship` |
| 拓扑 | **星型**：客户端 ↔ 房主 ↔ 其他客户端。AI 船的动态只从房主发出 |

**产出物**：`scripts/net/`（会话、转发、序列化、插值）、房间 UI、`tests/test_net_loopback.gd`。

## 5. 架构与接口约定

这一节是"实现者不需要再决定"的部分。更细的字段清单、消息清单、升降级规则写在 `docs/14-状态与网络架构.md`（M1 的第一件事就是把它写出来）。

### 5.1 状态三层与权威归属

| 层 | 谁写 | 装什么 | 怎么传 |
|---|---|---|---|
| `WorldState` | **房主** | 世界时钟与日期、风（种子 + 突变事件序列）、全局事件旗标、港口库存与价格、已发现地图、AI/NPC 抽象船 | 房主广播，客户端只读覆盖 |
| `ShipState` | **拥有者** | 位姿、艏向、帆角与帆档、三处损伤、资源与仓容、锚、船长/登陆队位置、名册摘要 | 拥有者 → 房主 → 其他客户端，20Hz |
| `Ship`（细化运行时） | **拥有者** | 气动、船员名册（40 人逐人状态）、寻路、需求循环 | **不过网** —— 别人不需要，也不该有 |

**为什么这样分**：v0.1 已经把"一条船"的模拟做成了自洽的一块（`ShipDynamics` + `Crew` + `CrewRoster` + `Voyage` 的接线）。把它整块搬到"拥有者本机"，别人的船只同步 `ShipState` 摘要，就等于**每台机器永远只细化一艘船** —— 负载和今天一模一样，四艘船同屏也不会集体卡（这是这套架构最大的好处，也是不需要把 40 人缩编的原因）。

### 5.2 世界查询：签名不变，实现换掉

`Sea` 现在的接口 `is_land / is_beach / is_reef / is_port / current_at / lee_factor / poi_at` **全部保留原名与签名**，实现改成走 `WorldMap`。这样 `Voyage`、`sea_debug.gd`、以及 `test_world` 里那一批调用点都不用重写，风险从"重写世界"降到"替换一层实现"。

硬性约束：**同一世界坐标，无论从哪个 tile 查询，结果必须完全一致**（这是 M2 的唯一硬指标）。

### 5.3 抽象船 ↔ 细化船

```
attach_player(ship_id)   抽象 → 细化：按同一份船员数据集生成名册，沿用抽象数值（船体%/货物/位置/航向）
detach_player(ship_id)   细化 → 抽象：丢掉逐人细节，只留汇总（船体%/人数/货物/行动状态）
```

**推论（必须写进 UI 的规矩）**：不允许进入别人的船的内部视图 —— 别人船上没有逐人模拟，只有外观与汇总数值。滚轮沉入船舱只对**自己那艘船**有效。

### 5.4 存档

`user://saves/<slot>.json`：`version / saved_at / world / ships[] / journal / story`。
版本不符 → 直接拒绝并提示，不做迁移（v0.5 内不承诺向后兼容，这一条写进文档就不算坑）。

### 5.5 铁律不变

1. **只有 `ShipDynamics` 写船的位置与速度** —— 现在是"每个 owner 写自己那艘"，`tools/check_motion_ownership.py` 扩展成按 owner 检查；
2. 玩家不直接操船（只能给目标点/帆档/人员），船员执行；
3. 剧情、UI、网络层都不许碰船；
4. 船是数据不是代码（改船 = 改 `tools/gen_ship.py` + 重新生成）；
5. 甲板外形与船壳轮廓同源（`WIDTHS`）。

## 6. M6 的数据真源与硬指标（陆战与火器）

### 6.1 武器真源

`data/defs/weapons.json` —— 与 `data/defs/ship_physics.json` 同等地位：**数值只有这一份**，GDScript 与离线标定脚本都读它。配套一个 `tools/weapons_prototype.py`（仿 `tools/aero_prototype.py`），用来离线扫参数、验证硬指标、生成命中率查表。

| 武器 | 口径 | 装填 | 有效射程 | 备注 |
|---|---|---|---|---|
| 火绳枪 Arquebus | 12–18 mm | 30–60 秒（熟练 20–30） | 100–150 m | 需火绳持续燃烧；雨天/受潮哑火；主要靠**齐射** |
| 回旋炮 Swivel gun | 20–40 mm | 1–2 分钟 | 100–200 m（霰弹） | 1–2 人操作；打人员 |
| 隼炮 Falconet | 50–60 mm，弹重 0.5–1 kg | 2–5 分钟 | 1000–1500 m | 2–4 人操作；登陆时拆下抬上岸；打结构/船体 |
| 长矛 / 剑盾 | — | — | 近战 | 火器装填期间的全部战斗力；被近身时决定结果 |

### 6.2 四项硬指标（与气动的四项硬指标同一套路）

这四条是**分水岭**：任何一条不成立，就说明火器模型只是"有烟有响"。

| # | 硬指标 | 判定方式 |
|---|---|---|
| 1 | **火绳枪打不出连发**：两发之间的间隔 ≥ 30 秒（实测射速 ≤ 2 发/分钟）；隼炮每发 ≥ 120 秒 | 无头跑 5 分钟战斗，统计射击次数 |
| 2 | **齐射才有杀伤**：同样 10 个人，密集齐射的总伤害 ≥ 各自为战的 **1.8 倍** | 命中率按"技能 × 距离 × 队形密度"查表 |
| 3 | **雨天真会哑火**：干燥哑火率 ≤ 5%，大雨 ≥ 30%；火药受潮后武器直接不可用 | 两种天气各跑一场，统计哑火 |
| 4 | **弹种不能互换**：霰弹对人员的杀伤集中在 100–200 m 内、对船体损伤 ≤ 实心弹的 10%；实心弹对人员威胁极低 | 两种弹 × 两类目标，四种组合的伤害表 |

### 6.3 三条实现约定

1. **确定性**：命中与伤害不用随机数 —— 用"技能 × 距离 × 队形密度 × 武器"查表 + 确定性偏差（沿用项目既有做法：可复现的正弦/哈希）。这样无头可测、联机可复现、出问题能逐发复盘。
2. **联机判定归属**：射击方只广播"谁向谁开火"；**由受击方所属的权威判定命中并广播结果**（AI 与文明群体归房主，玩家队伍归玩家本人）。否则两边的伤亡名单会不一致。
3. **船对岸双向**：船上炮位 → 岸上目标，岸上武装 → 停泊的船。船体/帆/人员的损伤全部复用 v0.1 已有的三处损伤链路（船体→阻力、桅杆→帆面积、舵→转舵效率），不新开一套。
