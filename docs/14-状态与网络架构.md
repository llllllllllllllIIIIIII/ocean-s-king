# 状态与网络架构（v0.5 · M1 定稿）

> 这份文档回答三个问题：**一局里有哪些状态、每一份归谁写、怎么存下来**。
> 它是 M1 的产出，也是 M3（局域网层）的地基 —— 网络的本质就是"把该传的状态传过去"，
> 所以状态边界必须在动网络代码之前定死。对应 `docs/13-v0.5开发计划.md` 第 5 节。

---

## 1. 为什么要分层

v0.1 是"一局 = 一条船"，所有状态都长在 `Voyage` 上。到了 v0.5，世界里同时存在 **4 艘远征船 + 若干 NPC 船**，于是同一个问题会有两种答案：

> "风是谁算的？你的船位是谁算的？"

如果回答不一样，就会出现"我这儿风已经转了、你那儿还没转"这类没法排查的漂移。所以先分层：

| 层 | 谁写 | 装什么 | 上网吗 |
|---|---|---|---|
| `WorldState` | **房主** | 时间、风、全局事件与剧情、航海日志、港口库存与价格、已发现地图、AI/NPC 抽象船 | 房主广播，客户端只读覆盖 |
| `ShipState` | **那条船的拥有者** | 位姿、帆与锚、损伤、指令、航海官、船员执行层、名册、登陆队 | 拥有者 → 房主 → 其他人，20Hz |
| 细化运行时 | 同上 | 气动积分、40 人逐人需求与寻路、登陆队的实时位置 | **永不直接上网**（别人只需要摘要） |

**最大的好处**：每台机器永远只细化**一艘**船（自己那艘）。四艘船在同一个世界里，单机负载和 v0.1 一样，所以**不需要把每船 40 人缩编**。

**必然推论（写进 UI 规则）**：别人船上没有逐人模拟，所以**不允许进入别人的船的内部视图** —— 只能看外观与汇总数值。滚轮沉入船舱只对自己那艘船有效。

## 2. WorldState 的字段清单

房主权威。字段名与 `scripts/world_state.gd` 一一对应，不许有第二个真源。

| 分组 | 字段 | 说明 |
|---|---|---|
| 时间 | `t` | 游戏时间（秒），从出港算起 |
| | `day` | 1519-09-20 起的天数。M2 起由**日历**算出（儒略历，`VoyageJournal.date_parts`），不是独立真源 |
| 风 | `wind_base_tws` `wind_base_from_deg` `wind_gust_gain` `wind_dir_swing` | 风场基准参数（`base_from_dir` 会被"风向突变"事件改，所以要存） |
| | `wind_tws` `wind_from_deg` `wind_t` | 风场的当前值（缓变正弦的结果） |
| 全局事件 | `fired` | 已触发的脚本事件旗标（瞭望 / 风向突变 / 触礁 / 伤病 / 遗迹 / 村落 / 上岸…） |
| | `island_known` `visited` `reef_hit` | 剧情与发现 |
| 地图 | `discovered` | 已"看见过"的 16km 分块（tile 键 `"x,y"` → true）。M2 起海图的雾就是它 |
| | `known_places` | 已经认得名字的陆地与港口（特征 id → true）。没认得的连名字都不写 |
| 船队 | `fleet` | **除本机以外**的船位（AI 船 / 别人的船）的摘要。M3 起世界里有固定 4 艘船 |
| 港口 | `ports` | 四个港口的库存（`{"stock": {港口: {货: 数量}}}`）。**价格是从库存算出来的**，所以不用存（M4） |
| | `shortage_events` | 欠过几次粮（M4 起记，M5 用来算士气） |
| 自然 | `weather` | 天气状态与它已经持续了多久（M7）。同一片海对所有人一样，所以是世界状态 |
| 事件 | `events` | 事件池里已经发生过哪些、触发顺序（M7） |
| 知识 | `knowledge` | 发现即记录：海图/物种/文化/语言/贸易/战争情报（M7） |
| | `memory` | 世界记住玩家做过什么：贸易 / 毁约 / 打捞 / 知识 / 杀伤（M7） |
| 剧情 | `story` | `head` / `objective` / `ending_ready` / `flags` / `steps_done` / `beat_time` |
| 日志 | `journal` | `entries` / `decisions` / `landfalls` / `last_line` / `distance_m` / `teleports` |
| 展示 | `last_message` `message_timer` | 消息条 |
| | `log_lines` | 可读日志行（HUD / 面板用） |
| 岸上 | `pending_reports` `shore_cooldown` | 船长离船期间攒下的报告、蹭滩提示冷却 |

**静态数据不进存档**：`Sea` 的地形/港口/地标、`Story` 的剧本正文、`ShipPhysics` 的物理参数、`trim_table` 全部来自仓库里的 JSON，读档时重新加载即可。**存档只存"会变的值"** —— 这是 `AGENTS.md` 铁律 1 的同一条道理。

## 3. ShipState 的字段清单

每条船一份（`ships[]` 数组）。v0.5 的单机模式下数组里只有 1 条；M3 起有 4 条，其中 3 条是抽象船（只有摘要字段）。

| 分组 | 字段 | 说明 |
|---|---|---|
| 身份 | `id` / `kind` | `player`；`detailed`（细化，有船员名册）/ `abstract`（抽象，只有数值） |
| 运动 | `pos` `heading` `u` `w` `heel` `yaw_rate` `rudder` | 与 `ShipDynamics` 的内部状态一一对应 |
| 帆与锚 | `sail_main` `sail_jib` `sail_area_scale` `anchored` | |
| 损伤 | `damage` | 船体 / 桅杆 / 舵 |
| 环境缓存 | `current_world` | 这一帧灌进来的洋流（M2 起由 `WorldMap` 提供） |
| 指令 | `orders` | 目标点、帆档、锚、操帆人手 |
| 航海官 | `nav` | 航法、目标航向、受风舷、换舷与抢风计数、迟滞状态 |
| 船员执行层 | `crew` | 目标攻角、收放速度、偏差、舵积分、内部计时 |
| 名册 | `roster` | 40 人逐人状态 + 排活计时 + 船上日志 |
| 登陆 | `ashore` `captain_pos` `captain_target` `landing_point` `ashore_count` | 船长与队伍在哪 |
| | `landing_land_id` | 上岸点踩在**哪块陆地**上（队伍的活动范围由它决定）。形状本身是静态世界数据，所以只存 id，读档时按 id 找回来 |
| | `party` | 登陆队每个人的位置与状态（`onboard` / `rowing` / `ashore`） |
| 资源 | `cargo` | 货舱（M4）：装了什么、有多少钱、缺过多少粮。`defs` 与载重上限是静态的，不进存档 |
| | `docked_port` | 现在靠在哪个港（空 = 在海上） |
| 社会 | `rules` | 玩家定的六条规矩（M5）。每条船有自己的规矩 |
| | `society` | 关系（66 对）/ 三伙人的凝聚力 / 紧张度 / 纪律 / 事件计数（M5） |
| | `dilemmas` | 三个高压抉择：答过哪些、哪个还挂着（M5） |
| | `ending_score` | 五类成果的分数（M8 的结算页读它，抉择会改它） |
| 当地文明 | `culture` | 三档态度与态度值（M6）。v0.5 只有一艘玩家的船在跑，所以暂时挂在本船；M7 挪进 WorldState 只要换容器 |

> **不存档的运行时**：`Voyage.battle`（正在打的那一仗）。它每一帧都在变，
> 而且只活在"船长在岸上"的这段时间里 —— 存下来没有意义（读档回去等于重打一遍）。
> 打完之后的**结果**（谁死了、态度变没变、结算扣没扣）全部落在名册、`culture`
> 与 `ending_score` 里，那些是存的。
| 抽象船专用 | `hull_pct` `crew_count` `cargo_summary` `action` | 抽象船只有这几个（原设定第二十一节的形状） |

> **M2 补一条"静态数据不进存档"的例子**：`ShipDynamics.land_shapes`（船撞哪些干地）
> 是 `WorldMap.land_shapes()` 算出来的纯数据形状表，和 `land_center` / `land_radius`
> 一样由 `setup()` 重新灌 —— **不进存档**，也**不是引用**（`ShipDynamics` 不持有 `WorldMap`，
> 避免引用环）。

> **M4 的摘要**：船位摘要在 M3 的 9 个键上加了 `hold_kg`（装了多少）与 `money` ——
> 别人的船能看到的就这两样，货舱里具体装了什么**不过网**。

## 4. 存档

### 4.1 位置与形状

```
user://saves/<slot>.json
{
  "version": 1,
  "saved_at": "2026-10-02 14:33",
  "slot": "auto",
  "world": { ...WorldState... },
  "ships": [ { ...ShipState... } ]
}
```

### 4.2 三条规矩

1. **版本不符直接拒绝**：读出 `version != SAVE_VERSION` → 不加载、不改内存，把失败原因返回给 UI。v0.5 内**不承诺向后兼容**，也不写迁移代码（写迁移比丢存档更贵）。
2. **只存会变的值**：静态数据（船体布局、物理参数、剧本、海域）不进存档，读档时重新加载。
3. **失败要能被用户看见**：读档失败必须给一句人话（"这个存档是旧版本，v0.5 打不开"），不许静默失败。

### 4.3 浮点精度（实测结论，别踩第二次）

Godot 的 JSON **不保证 double 精确往返**：实测 `1/3` 存进去再读出来会掉到 15 位有效数字（`var_to_bytes` 是精确的，但二进制不利于人看与手改）。

因此：

- 存档用 **JSON**（可读、可手改、可 diff），代价是连续量有 ~1e-15 的相对误差；
- **离散状态必须精确相等**（剧情旗标、船员所在格子、岗位、损伤、锚、帆档、发现记录）；
- **连续状态允许极小误差**（位置 / 艏向 / 速度），测试用容差断言而不是位相等；
- 读档后继续跑，要求"连续量在容差内一致 + 离散状态完全一致"。

> 这条决定了 `tests/test_save.gd` 的断言口径 —— 不是偷懒，是 JSON 的物理限制。

## 5. 为 M3 预留的网络投影

> **M3 已实现**（2026-10-01）：消息清单与实际收发见 `docs/16-局域网层.md` §4，
> 代码在 `scripts/net/`。下面这张表是 M1 当时定下的形状，实现与它一致
> （实际还多了两条控制消息：`bye` 与 `full`）。

| 谁 → 谁 | 发什么 | 频率 |
|---|---|---|
| 拥有者 → 房主 → 其他客户端 | `ShipState` 的**投影**：id / 位姿 / 帆角 / 帆档 / 锚 / 损伤 / 人数 / 登陆队摘要 | 20 Hz |
| 房主 → 全部客户端 | `WorldState` 全量（变化时）+ 增量（风与时钟） | 0.5 s |
| 客户端 → 房主 | 玩家指令（目标点 / 帆档 / 抛锚 / 调人手 / 陆战开火宣告） | 事件驱动 |

**不上网的东西**：40 人逐人需求与寻路、烟幕粒子、相机、UI 状态。

**权威归属的三条硬规则**（M3 / M6 都要遵守）：

1. 谁的船谁写：客户端不接受别人对"我的船"的写入；
2. 世界只有房主能改：客户端算出的风 / 时间 / 港口价格一律被覆盖；
3. **命中与伤害由"受击方所属的权威"判定** —— 射击方只广播"谁向谁开火"（M6 陆战靠这条才能两边一致）。

## 6. 抽象船 ↔ 细化船

```
attach_player(ship_id)   抽象 → 细化：按同一份船员数据集（data/defs/crew_12.json）生成名册，
                                   沿用抽象数值（位置 / 航向 / 船体% / 货物 / 行动状态）
detach_player(ship_id)   细化 → 抽象：丢掉逐人细节，只留 hull_pct / crew_count /
                                   cargo_summary / action / 位置 / 航向
```

**关键约束**：升降级必须**幂等且可重复** —— 同一条 AI 船被接管、掉线、再接管，不能每次生成一套完全不同的名册（否则"我的船回来以后船员全换人了"）。
做法：名册用**船 id 做种子**确定性生成（沿用项目既有的"不用随机数、用确定性哈希"的规矩）。

## 7. 怎么保证它不腐化

存档系统最容易死于"有人加了一个字段忘了存"。两道护栏：

1. **字段覆盖断言**：`tests/test_save.gd` 用 `get_property_list()` 取出每个参与存档的类的**脚本变量**，和序列化出来的键做对比 —— 少一个就报错并写出字段名。
   显式豁免（纯派生量、静态表、明确临时的字段）写在测试里，且必须在代码注释里说明理由。
2. **往返 + 继续跑**：存 → 读 → 离散状态精确相等、连续状态在容差内；再各自跑 300 秒游戏时间，仍然一致。

只要这两条在，后面 7 期往里加字段就不会把存档搞坏。
